Question & Answer Types

What can people ask, given the RTT API as our data source?

The RTT API gives us two data shapes

Location Search
List of services at a station, optionally filtered to another station. Includes: times, platform, operator, lateness, countdown.
Service Detail
Full calling pattern for one train. Every stop with scheduled & realtime times, platforms, cancellation info.

Question Types & What Answers They Need

Question a human asks Answer shape API call
"When's the next train from Highbury to Moorgate?" A → B single best match Location(A, to=B) → first result
"What trains go from Highbury to Moorgate this afternoon?" A → B list Location(A, to=B, time)
"What's leaving from Kings Cross?" A → ... list Location(A)
"What's arriving at Paddington?" ... → B list Location(B, arrivals=True)
"Is the 14:30 from Kings Cross on time?" Status single service Location(A, time) → match → Service(uid)
"What platform is my train?" Status single fact Location or Service → platform field
"Where is train G12345 right now?" Journey calling pattern Service(uid, date)
"Show me the full route of this train" Journey calling pattern Service(uid, date)
"How are trains running on the Northern line today?" Overview aggregate Location(A) → aggregate lateness across services

Answer Type Taxonomy

A → B (Route)
Full origin-destination pair. The most common real question. Can be a list (timetable) or single (next train).
API: Location(station, to_station)
A → ... (Departures)
Half-answer: what's leaving from here? User browses destinations. Board-style display.
API: Location(station)
... → B (Arrivals)
Half-answer: what's coming in? "When does Dad's train get here?" Meeting someone.
API: Location(station, arrivals=True)
Journey (Calling Pattern)
Full route of one train: every stop, with progress indicator showing where it is now.
API: Service(uid, date)
Status (Single Fact)
Platform, delay, on-time — extracted from either endpoint. Often a follow-up to a list.
API: derived from Location or Service
Overview (Aggregate)
Computed from multiple services: "how's it running today?" Average lateness, cancellation rate.
API: Location(station) → compute stats

Key Insight

The API gives us two primitives (location list + service detail), but users think in six answer types. The CLI's job is to bridge that gap — translating human questions into API calls and presenting the right answer shape.

Some answers need chaining: "is the 14:30 on time?" requires a location search to find the service, then a service query for detail. The CLI should handle this transparently.
