CLI Command Structure

How should the commands be organized?

A

Mirror the API

Commands map directly to RTT endpoints

tt search HIB                    # location departures
tt search HIB --to CHX           # filtered
tt search HIB --arrivals         # arrivals
tt service A12345 2026-03-13     # service detail

Pros

  • 1:1 with API — predictable
  • Simple to implement

Cons

  • "search" isn't intuitive for casual users
  • No higher-level workflows
B

User-Friendly Verbs

Natural commands with higher-level features built in

tt departures highbury            # live departures
tt arrivals "kings cross"         # arrivals
tt departures home --to work      # using aliases
tt next home --to work            # next train only
tt journey HIB CHX                # full journey detail
tt service A12345                 # service detail (today assumed)
tt alias set home HIB             # save an alias

Pros

  • Intuitive for casual users
  • "next" command is high-value
  • Aliases feel natural

Cons

  • More commands to learn
  • More surface area to maintain
C

Hybrid — Friendly Defaults, API Depth

Casual-first commands with power-user flags for full API access

tt highbury                       # departures (default action)
tt highbury --to CHX              # filtered
tt highbury --arrivals            # arrivals
tt highbury --at 14:30            # specific time
tt highbury --on 2026-03-15      # specific date
tt next home work                 # next train shortcut
tt service A12345                 # service detail
tt alias home HIB                 # save alias
tt --json highbury                # raw JSON output

Pros

  • Minimal typing for common case
  • Station name IS the command
  • Full power via flags
  • Scriptable with --json

Cons

  • Magic default behavior needs clear help text
  • Station names could clash with subcommands
